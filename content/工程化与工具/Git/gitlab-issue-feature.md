## 题目

## 回答
ChatGPTGitLab Issue 是什么GitLab Issue 可以理解为项目里的“工作单”或“任务卡片”。它不只是记录 bug，而是用于把一个需要被处理、讨论、跟踪和交付的事项沉淀下来，例如：新功能需求缺陷 / 线上故障技术改造测试任务重构任务安全问题产品或用户反馈待确认的技术方案GitLab 官方对 Issue 的定位是：用于团队协作、规划、追踪并交付工作。它可以承载功能提案、任务、支持请求和 Bug 报告等。GitLab Docs+1一个 Issue 通常包含什么一个比较完整的 Issue，通常包括：信息作用标题说明要解决什么问题描述背景、需求、复现步骤、验收标准、技术方案等Assignee指定负责人Labels分类，例如 bug、`feature`、`P0`、`backend`Milestone归属某个版本、迭代或发布日期Due date截止时间评论区产品、研发、测试、运维讨论和决策记录状态Open / Closed，部分配置可进一步表达 To do、In progress、Done 等关联 Issue表达依赖、阻塞、重复、拆分关系关联 MR表明这个 Issue 最终由哪些代码变更解决GitLab 支持通过负责人、标签、截止日期、健康状态等维度组织和优先级管理 Issue，也支持评论和线程讨论。GitLab Docs+1最常见的使用场景1. 记录 Bug例如线上发现一个接口偶发 500：纯文本标题：
[Bug] 导出任务在大数据量下偶发超时

背景：
用户导出超过 10 万条数据时，部分任务失败。

复现步骤：
1. 创建包含 10 万条以上数据的项目
2. 点击导出
3. 等待任务执行

实际结果：
接口返回 504，异步任务被中断。

预期结果：
导出任务应在后台完成，并提供下载链接。

优先级：
P1

负责人：
后端 @xxx

验收标准：
- 10 万条数据可正常导出
- 导出任务不阻塞 HTTP 请求
- 失败时具备可观测日志和重试机制适合用于：测试提 Bug客服或产品反馈问题线上故障跟踪缺陷修复验收2. 管理一个功能需求例如产品提出“支持用户导出项目成员列表”。一个 Issue 可以把需求完整固化：纯文本标题：
[Feature] 支持导出项目成员列表

需求背景：
企业管理员需要定期导出成员信息进行权限审计。

范围：
- 支持 CSV 导出
- 包含姓名、邮箱、角色、加入时间
- 仅项目管理员可操作

非范围：
- 暂不支持 Excel 模板定制
- 暂不支持跨项目汇总导出

验收标准：
- 管理员可以发起导出
- 导出文件字段正确
- 无权限用户不可见入口
- 操作日志可追溯这样研发、测试、产品不会只靠口头或聊天记录理解需求。3. 把大需求拆成可执行任务例如“接入新的登录体系”是一个大需求，不能直接由一个人、一个 MR 完成。可以拆成多个 Issue：纯文本Epic：统一登录体系改造

├── Issue #101：梳理现有登录链路和依赖方
├── Issue #102：后端接入 OAuth 回调
├── Issue #103：前端登录页改造
├── Issue #104：用户数据迁移方案
├── Issue #105：补充登录链路监控和告警
├── Issue #106：回归测试与灰度发布方案GitLab 支持 Issue 之间建立双向关联，也可以表达依赖、阻塞、重复等关系。GitLab Docs这对你做架构改造、平台能力建设、AI Agent 项目尤其重要：一个 Issue 是可交付单元，不是模糊的“要做点什么”。4. 作为敏捷开发的任务看板Issue 可以放到 Issue Board 里，类似 Jira 看板、Trello、飞书项目看板。常见列设计：纯文本待评审 → 待开发 → 开发中 → CR 中 → 测试中 → 待发布 → 已完成每一个卡片就是一个 Issue。GitLab 的 Issue Board 支持按标签、负责人、里程碑、迭代等组织卡片，也可以拖动卡片推进工作流，适用于看板和 Scrum 等敏捷管理方式。GitLab Docs例如你可以定义标签：纯文本status::todo
status::doing
status::review
status::testing
status::done然后让 Issue Board 自动按这些状态展示。5. 连接“需求 → 开发 → 代码评审 → 发布”这是 GitLab Issue 最有价值的一点。典型链路：纯文本Issue
