一、大模型网关的需求背景是什么？解决了什么问题？
面试官想考察什么

主要判断你是否理解业务需求，以及为什么不能让每个业务方直接调用大模型厂商 API。

推荐回答
写作

我们做大模型网关主要是为了统一公司内部的大模型调用入口。

随着 AI 功能逐渐增加，不同业务会接入不同厂商的模型，比如 OpenAI、Anthropic、DeepSeek，或者第三方模型服务平台。如果每个业务都直接对接厂商 API，就会出现几个问题。

第一是重复开发。每个业务都需要分别处理 API Key、鉴权、模型协议、超时、错误码等逻辑。

第二是模型切换成本比较高。如果某个模型价格上涨、响应不稳定，或者业务想替换模型，就需要修改业务代码。

第三是缺少统一的治理能力。比如没办法统一管理不同业务的 Token 消耗、调用成本、请求量、错误率以及模型使用权限。

所以网关的核心定位，是在业务应用和模型提供商之间增加统一接入层，屏蔽不同厂商的协议差异，并集中管理模型路由、鉴权、限流和调用治理。

从架构上看，它与传统 API Gateway 类似，但会额外关注 Token 消耗、长连接流式响应、厂商限额以及模型能力差异。

2. 怎么区分慢在网关还是慢在模型？

假设用户反馈：调用一个模型耗时 20 秒。

你不能只看 http_request_duration_seconds。

最好把整个调用链拆开：

请求耗时拆解（示例数据）

网关鉴权 / 路由

30ms

连接 / 等待上游首字节

170ms

模型首段生成等待

2.8s

流式内容持续输出

17.0s

时间点需要在网关侧定义并明确测量。TTFT 通常从请求开始算至首个有效内容事件，不应与 HTTP 首字节时间混为一谈。

网关需要分别采集：

gateway_processing_duration：鉴权、协议转换、选路开销。

upstream_ttft：从发起上游请求到首个有效输出事件。

request_duration：完整请求总耗时。

active_streams：当前存活的流式请求数。

upstream_errors_total：按服务商与错误类型统计。

input_tokens / output_tokens：按模型和业务归集。

注意：TTFT 不等于 HTTP TTFB，因为某些模型可能先返回响应头、SSE 心跳或 Thinking 事件，之后才开始输出用户可见文本。

四、有没有做性能调优？高并发、高可用怎么部署？

这个问题可以分成三个方面：网关自身性能、上游模型容量、故障隔离和恢复。

1. 网关高并发的瓶颈在哪里？

很多后端工程师会直接回答：

Go 的 goroutine 比较轻量，可以支持大量并发请求。

这个回答不够。

对于主要做转发的 LLM Gateway，瓶颈通常不只是 CPU，而可能包括：

长连接占用： 一次流式请求持续几十秒甚至更久，同时占用连接、goroutine、内存以及文件描述符。

上游配额： 即使网关能处理上万连接，上游厂商可能只允许有限 RPM、TPM 或并发数。

客户端读取慢： 上游模型持续产生数据，但下游消费较慢，可能造成写阻塞和内存缓冲积压。

协议转换开销： 高频 JSON 解析、重复序列化、字符串拼接带来短生命周期对象和 GC 压力。

突发流量： 请求在同一时间到达，容易触发厂商 429，重试又可能放大负载。

特别注意：对于完整生成请求，吞吐能力可能主要受上游模型吞吐、TPM 和长连接占用影响，而不是网关的 HTTP QPS。

面试官很可能会追问：

“为什么 MaxConnsPerHost 设置成 200？如果上游是 HTTP/2 呢？”

关键点在于：连接数不等于请求并发数。HTTP/2 支持在一个连接上复用多个 Stream；实际容量还受服务端并发流限制、连接池行为和上游配额影响。

所以需要通过压测，而不是根据固定经验值设定参数。

比较完整的高可用方案包括：

网关无状态化，多 Pod 部署，避免单实例故障。

Readiness Probe 控制实例是否接新请求；Liveness Probe 只用于判断是否需要重启。

使用 HPA 根据 CPU、活跃流数量或排队情况扩缩容。

利用 PodDisruptionBudget、拓扑分散，降低节点故障和维护的影响。

滚动升级时先停止接收新连接，再给现有 SSE 流足够的优雅退出时间。

上游提供商独立熔断、限流和健康管理，避免一个厂商故障拖垮其他模型调用。

一个特别容易被问到的点是：

“Pod 滚动发布时，已有的 SSE 长连接怎么办？”

不能只说 Kubernetes 会优雅退出。

更完整的回答是：Pod 先从就绪端点摘除，进入 Draining 状态；不再接收新的业务请求，等待存量请求结束，同时协调 Ingress 的连接摘除、preStop、terminationGracePeriodSeconds 与 Go HTTP Server 的 Shutdown。超过终止宽限期仍未结束的流可能被中断，因此需要客户端有相应的异常处理策略。

3. 追问：你们有没有对大模型输出文本做处理？

这个问题要特别小心。

建议区分：

传输事件处理：解析、转换 SSE 事件，提取 Token Usage、工具调用、错误信息。

业务内容处理：对模型生成的文本做脱敏、敏感词检测、JSON 结构校验、审计等。

对内容处理而言，如果直接逐 Chunk 进行敏感词过滤，可能出现一个敏感词被分在两个 Chunk 中的情况。

如果需要完整语义检测，通常需要引入窗口缓冲或完整内容缓冲，这会增加延迟、内存占用和实现复杂度。

因此不能简单说“在每个 Chunk 里替换一下字符串”就完成了流式内容安全处理。

六、模型厂商已经处理了错误码，我们网关还需要再处理吗？

需要。厂商返回错误码，解决的是错误的描述；网关处理错误，解决的是错误的分类、隔离、恢复和向业务提供一致的失败语义。

这两者不是一回事。

比如上游返回 429，说明请求受到限流，但不会自动帮你选择其他服务商，也不会自动解决多个业务并发重试造成的流量放大。

2. 我建议你重点讲：统一错误分类

网关内部不应该只传递 HTTP Status Code。

可以定义统一错误结构：

Go
type GatewayError struct {
    Code       string
    Provider   string
    UpstreamCode string
    HTTPStatus int

    Retryable  bool
    RetryAfter time.Duration
    Cause      error
}

例如：

纯文本
Provider A: 429 rate_limit_error
Provider B: 429 quota_exceeded
Provider C: 503 model_overloaded

不同错误在网关内部可以映射为：

纯文本
RATE_LIMITED
QUOTA_EXHAUSTED
PROVIDER_OVERLOADED
AUTHENTICATION_FAILED
CONTEXT_LENGTH_EXCEEDED
UPSTREAM_TIMEOUT
STREAM_INTERRUPTED

重点是：相同的 HTTP 状态码不一定代表相同的恢复动作。

例如 429 可能是短时间速率限制，也可能是账户额度耗尽。前者可能适合退避重试或选择其他部署，后者继续重试同一账户通常没有意义。

3. 面试官追问：厂商 SDK 已经自动重试，为什么网关还要做？

这是非常有价值的深挖题。

你可以这样回答：

SDK 的重试通常只能针对当前厂商请求做局部恢复，而网关知道整体的租户配额、模型部署情况，以及其他厂商的容量状态，可以做跨部署故障切换。

但是必须明确重试由哪一层负责，否则客户端、网关和 SDK 同时重试会产生重试放大。我的设计倾向是将重试次数、总体超时和故障切换纳入统一预算，并限制重试链路。

4. 还有一个关键追问：SSE 已经返回一半，还能重试吗？

原则上，不应该将已经输出到客户端的生成内容自动切换上游并重新开始，然后伪装成同一条连续响应。

因为：

新的模型输出不一定与之前内容一致。

工具调用可能已经部分生成。

重试可能导致相同工具被重复调用。

响应头可能已提交，无法修改 HTTP 状态码。

更合理的策略是区分两个阶段：

重试决策

上游请求失败

判断发生在下游响应提交之前还是之后

尚未提交响应

可以考虑重试

检查可重试性、超时预算、部署健康状态，再决定重试或故障切换。

响应已提交

通常终止当前流

按目标协议报告流内错误；不伪造成功结束，记录部分输出和失败原因。

即使尚未提交下游响应，也不代表重试绝对安全，还需要考虑上游是否已执行有副作用的操作，以及是否支持幂等。

3. 面试官问：两个厂商都部署同一个模型，一个 429，另一个有容量，怎么处理？

推荐的逻辑是：

请求到达后，根据业务选择逻辑模型。

过滤掉已熔断、权限不符、能力不匹配或容量不足的部署。

根据权重或者配额选择 Provider A。

Provider A 返回 429。

解析错误类型与 Retry-After，更新该部署的限流状态。

如果请求还没有向客户端提交响应，检查剩余的请求预算。

Provider B 能力满足要求且有容量时，可以尝试切换。

记录每次尝试的 Provider、延迟、错误类型与最终结果。

如果使用多个网关 Pod，还需要考虑一个分布式问题：

某个 Pod 收到 429 后，其他 Pod 是否还会继续往同一个 Provider 发送请求？

如果每个 Pod 只维护本地限流状态，就可能出现多个实例同时打满同一个厂商限额。

因此可以在 Redis 中维护跨实例的配额或冷却状态，同时保留本地快速限流，减少每个 Token/请求都访问 Redis 的成本。

4. 同一个会话需要固定厂商吗？

不一定，但某些场景下需要。

比如不同厂商的 Prompt Cache 并不共享，或者客户端使用了厂商专属的多轮状态与工具调用机制。

这时要考虑 Session Affinity，让同一个会话优先使用同一个部署。

但如果请求完全无状态、上下文由客户端完整提供，跨部署切换可能更容易。

同时，一旦涉及 Thinking 签名、服务端状态或厂商私有能力，就不能只凭相同模型名称判断可切换性。

写作

我们公司内部有多个 AI 相关业务，包括大模型调用和 Agent 类应用。最初不同业务可能需要分别对接模型厂商，因此需要一个统一的大模型接入层。

这个网关主要负责统一模型访问入口，屏蔽不同模型平台的协议差异，并集中处理模型路由、调用鉴权以及相关治理能力。

我参与过这套网关的接入和维护。技术上，我认为它和传统 API Gateway 最大的区别，在于大模型请求通常耗时较长，而且大量使用 SSE 流式响应，同时不同厂商还存在 Token 配额、调用限速和协议差异。

所以这类系统的工程重点主要有三个。

第一是流式请求处理。 需要区分纯 SSE 透传和协议转换场景，处理长连接、客户端取消、事件边界以及 Tool Calling 等问题，避免增加不必要的首 Token 延迟。

第二是上游服务治理。 不同厂商对 429、超时和服务过载的处理机制不完全一样。网关需要统一错误语义，根据错误类型、请求阶段和剩余超时预算决定是否重试或切换部署，避免重试放大。

第三是可观测性和容量管理。 与传统 HTTP 服务相比，除了 QPS、P95 和错误率，还需要关注 TTFT、活跃流数量、Token 消耗，以及不同上游模型的延迟和错误分布。

从架构设计上，这类网关需要尽量保持无状态、支持多副本部署，并把模型协议适配、选路和治理能力解耦，这样后续增加新的模型厂商会更容易维护。

这份回答可以作为项目技术阐述框架，但还不是最终的个人项目业绩版本。建议你在实际面试时进一步区分：哪些能力是现有网关已有的，哪些是你参与维护的，哪些是你分析后认为需要优化的。
